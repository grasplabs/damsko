# Damsko

Grasp's design system: primitives and a few generic blocks, built on StyleX and UI SDK, named the way shadcn names things, and published as a shadcn registry. Products install the source with the stock shadcn CLI and compose their own components from it. The repository is public and the licence proprietary (`LICENSE`).

## Layout

| Path | What it is |
| --- | --- |
| `tokens/` | Token source and generator; never shipped |
| `src/` | What ships, at the paths it lands at in a product: `components/` (one file per primitive, three folder components), `blocks/`, `lib/`, `hooks/`, `styles/` |
| `examples/` | One folder per component, one file per example |
| `docs/` | The docs pages (MDX) |
| `site/` | The Astro docs site, deployed with the registry to damsko.joingrasp.com |
| `scripts/` | Repo tooling, run by Node directly (TypeScript, no build step): the registry generator, the static gates, the tree guard, the hooks' checks, the specs' server and the unit tests (`*.test.ts`) |
| `tests/` | The browser specs, Playwright Test against the built site: one per component (`tests/<component>.spec.ts`) and one per rule that holds across the library (`focus`, `forced-colours`, `touch-targets`, `phone-fields`, `csp`, `scrolling`, …) |
| `registry.json` | The registry's source, generated by `pnpm generate`; `shadcn build` writes `dist/r/` from it in `pnpm build` |

## Commands

Vite+ (`vp`) is the toolchain. Run from the repo root:

- `vp install`: install dependencies (also installs the git hooks)
- `vp check`: format, lint (Ultracite) and type-check; `vp check --fix` to fix
- `node scripts/gates.ts`: the static gates (generated files current, registry, React Compiler, no memo, words, props tables, API tables, conventions, every component's target API and shape, every component's spec, example and page under its name, product knowledge, ES2023, the diff engine)
- `node scripts/guard.ts`: what may be in the tree
- `node scripts/check-install.ts`: every item installed with the stock shadcn CLI into a fresh project, from the registry built here: byte for byte, only the packages the items name, type-checked (installs from npm, about half a minute)
- `vp test`: unit tests
- `vp run test:browser`: the browser specs in Chromium, against `dist/` (build first); `vp run test:browser tests/<name>.spec.ts` for one
- `vp run dev`: the docs site at localhost:4517; `vp run build`: the static site and the registry into `dist/`
- `vp run generate`: tokens, themes and `registry.json`; commit what it changes

`vp run check` runs `vp check`, the guard and the gates. CI (`.github/workflows/ci.yml`) runs all of them, the secret scan (`vp run check:secrets`), the unit tests, the build, the install check and the browser specs in four shards (Chromium on every pull request and in the merge queue, Firefox and WebKit nightly); `.github/workflows/pull-request.yml` checks the pull request's title and that nothing credits an AI tool. Vite+ docs: `node_modules/vite-plus/docs`.

## What belongs in Damsko

- **Primitives and a few generic blocks.** Nothing in Damsko knows a Grasp concept: chats as product data, agents, Apps, workflows, the Brain, connections, providers, copy that names Grasp, Lingui, the router.
- **Product content comes in through a slot or a render prop.** A part never grows a product feature.
- **A new part enters only when shadcn has it**, or a second product needs it and its product knowledge is taken out first. A product need a part does not cover becomes a component in that product.
- **One file per primitive**, plus `<name>.stylex.ts` when it defines markers or variables (StyleX requires that name). Three components are folders, and only these: data-table, data-grid and markdown, each with an `index.ts` whose first sentence says why. Everywhere else a pure helper sits beside its component as a sibling `<name>-<what>.ts` (`chart-math.ts`, `diff-viewer-diff.ts`, `code-block-prism.ts`), never in a folder.
- **A block is a folder**, `src/blocks/<name>/<name>.tsx`, because the registry ships each block as a folder (`registry:block`); a product imports it as `@grasp-os/ui/blocks/<name>/<name>`.
- **Names come from shadcn first, then the wider industry**: file names, parts, props, variant and size values (`xs`, `sm`, `default`, `lg`, `icon`; there is no `md`). No house vocabulary.
- **No barrels**, no `index.ts` outside the three folder components, no deprecated aliases, no compatibility shims, no dead code.
- **The primitives' few built-in words come from the `I18nProvider`.** No per-component word files.
- **Not in the brand book, not in Damsko**: colours, tokens, effects. Every colour, space, corner, edge, shadow, time and curve is a token.
- **Source layout equals installed layout.** Every registry file is typed `registry:file` with a `~/src/…` target, imports are relative, npm dependencies are listed by name only, and the registry's files are built with `shadcn build` at deploy, never committed (`scripts/check-registry.ts`).
- **Every component has a spec** that selects by role, label or text, an example and a docs page, changed in the same pull request as the component; its files and exports are pinned in `scripts/target-api.json` (`scripts/check-target-api.ts`), and the spec, the examples folder and the page carry its name (`scripts/check-coverage.ts`).

## How a component is made

- **shadcn's structure and names lead.** A component has the parts, props and composition shadcn gives it; an AI part has those of shadcn's AI Elements. Damsko changes the look, not the shape.
- **One shared implementation.** Two parts that do the same thing share one implementation, in `lib/` or in the component they build on; never two copies that drift apart.
- **Each variant has its own purpose and its own look.** Two variants that do the same job, or look alike, are one. Button's six: `default`, the one main step of a view; `outline`, the ordinary button: the lesser action beside a main one, and a standalone action or trigger; `secondary`, a quieter, flat alternative for a dense place where several outlined buttons would be too many edges (a row of filters or chips, an action inside a card); `ghost`, toolbars, rows and icon buttons; `destructive`, what cannot be undone; `link`, an action that reads as words.
- **A deviation from shadcn stays only when it gives the person using the interface something real**, and is done simply. Otherwise shadcn's way stands.
- **Content from a model or another user is untrusted.** A link given as data goes through `safeHref` (`lib/utils.ts`: http, https and mailto only; a path on the same site only with `relative`); a picture, sound or video given as data through `safeMediaSrc` (a `data:` picture, sound or video, never SVG, a `blob:` or a path on this site; a remote `http(s)` address only when the part's `allowRemote` says the source is trusted); a key that comes from content or data is read with `ownValue`, never by indexing an object; content is never written as HTML (no `dangerouslySetInnerHTML`, no `innerHTML`).
- **A message only a developer reads** (a console warning, a thrown misuse) is an English literal in the component, never a catalogue entry.

## Rules every component passes

The product builds Damsko's source with its own toolchain, so every component passes the product's rules: the same formatting, lint and strict types (`vp check`), the React Compiler at `panicThreshold: "all_errors"` with no hand-written memoisation, StyleX's compiler, every visible word a prop, tokens only, motion within 300 ms that grows from its trigger, hidden scrollbars that keep the wheel, one height per size, keyboard and screen reader first. `CONTRIBUTING.md` has the full list and the check behind each.

## Conventions

- **Commits and PR titles** follow [Conventional Commits](https://www.conventionalcommits.org). The scope is the component or area: `feat(button): …`, `fix(dialog): …`, `docs(tokens): …`, `ci: …`. Pull requests are squash-merged, so the title is the commit on `main` and the changelog entry. A `commit-msg` hook and CI enforce it.
- **Dependencies**: versions live in the `catalog` in `pnpm-workspace.yaml`, pinned exactly, the toolchain's at the product repo's versions; `package.json` references them as `catalog:`. New versions wait 3 days (pnpm and Renovate). Renovate opens one pull request for the toolchain and everything the components import, which never merges itself (`.github/renovate.json5`); only the docs site's own dependencies and the actions merge themselves. Only packages listed under `allowBuilds` may run install scripts.
- **No dev docs in the repo**: plans, notes, studies and session state live outside it. The Markdown allowed is `README.md`, `CONTRIBUTING.md`, `CHANGELOG.md`, this file, `.github/` templates, the docs pages in `docs/` and `THIRD_PARTY_NOTICES.md`; agent skills are installed locally, never committed. Put the why in code comments where the decision sits, and in pull request descriptions.
- **Pictures, video and audio live only under `public/`**, and only as assets the site shows: its own, the brand book's, fonts, logos, example fixtures. No screenshots that prove a change: they go in the pull request description. No file over 1 MB, and none that nothing refers to. The guard in CI (`scripts/guard.ts`) enforces it and names the files and folders `public/` may hold.
- **The repository is public**: no secrets, client names, staff names or internal notes in code, comments, issues or pull requests. Workflows run on `pull_request`, never `pull_request_target`, and give no secret to a pull request from a fork.
- **No compatibility code**: Grasp has no clients yet. Every change is a hard cut: no backwards compatibility, legacy layers, deprecated aliases or dead code.
- **No AI attribution**: no co-author trailers or "generated with" lines in commits or pull requests. The `commit-msg` hook and CI enforce it.
- **Never skip the git hooks** (`--no-verify`), and never loosen a lint rule to make code pass: fix the code. The rules `vite.config.ts` turns off for `examples/` and `site/` are what those folders do not pass; none is added, and each comes back on as its folder passes it.

## Branches and pull requests

Trunk-based: `main` is the only long-lived branch. The site and the registry are built from it; no CI job deploys them.

1. Branch from `main` as `<type>/<kebab-description>`, e.g. `feat/button-icon-sm`, using the commit types. A `pre-push` hook and CI check the name.
2. Open a **draft** pull request into `main`. Screenshots of any change that shows go in its Screenshots section, light and dark.
3. Have the diff reviewed by a reviewer that didn't write it (a fresh agent with no context from the author is fine) for correctness, simplicity and the rules above. Fix what it finds and review again, until a round finds nothing of medium severity or worse.
4. Add it to the merge queue (`gh pr merge --squash --auto --match-head-commit <sha>`), which runs CI on top of the latest `main` and squash-merges it.

Nobody pushes to `main` directly. The rules live in `.github/rulesets/main.json`; CODEOWNERS are requested as reviewers.

## Testing

Test what the code does, through its real interface, never how it does it. Unit tests (Vitest, `scripts/*.test.ts`) are for pure logic; behaviour in a browser belongs in the component's spec (`tests/<component>.spec.ts`, Playwright Test on its example pages, selecting by role, label and text), and a rule across the library in its topic's spec. How to write and run one, and the definition of done for a component, are in `CONTRIBUTING.md`. No tautological, change-detector or absence tests; keep suites flat, and never commit `.only` or `.skip`.

## Code standards (Ultracite)

This project uses the product repo's **Ultracite** presets for Oxlint and Oxfmt, loaded through Vite+ in `vite.config.ts`. Run `vp check --fix` to format and fix. Full reference: `node_modules/ultracite/skills/ultracite/references/code-standards.md`. Write code that is accessible, performant, type-safe and maintainable: explicit types at boundaries, `unknown` narrowed before use, no non-null or unchecked type assertions, early returns, no barrels, semantic HTML with the ARIA it needs.
